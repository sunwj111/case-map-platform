# 清洗知识库：接口写法规范

清洗时要把接口挂到功能用例上，知识文件必须让系统同时看见两件事：**功能点名称**、**HTTP 方法 + 路径**。只写 Java 方法名、Dubbo、调用链，通常挂不上。

推荐 Markdown（`.md`）。历史用例里的「功能点」列尽量与知识里的功能点同名。

## 写法一（优先）：功能点下面直接写接口

```markdown
场景：签约提交

功能点：签约提交
接口：POST /contract/submit
规则：合同状态必须为待提交

功能点：签约撤回
接口：POST /contract/revoke
```

一条功能点可以写多条 `接口：`。路径必须以 `/` 开头，方法和路径之间用空格，例如 `POST /foo/bar`。

## 写法二：接口表带功能点列

接口很多、集中成表时，**必须有「功能点」列**，不要只写方法和路径。

```markdown
## 功能点
- 签约提交
- 签约撤回

## 接口
| 功能点 | 方法 | 路径 |
|---|---|---|
| 签约提交 | POST | `/contract/submit` |
| 签约撤回 | POST | `/contract/revoke` |
```

列名可用：`功能点` / `功能`、`方法`、`路径`。

## 不要这样写

| 写法 | 结果 |
|---|---|
| 接口全部堆在「五、接口」里，没有功能点列 | 接口能抽出，但批不到对应功能用例 |
| `CostAuditApi#accept`、`submitDesignCost(...)` | 不保证抽成 HTTP 接口 |
| 只有 `/costAudit` 这种类级 mapping | 会丢掉 |
| 功能点叫「人工审核」，接口挂在「审核通过/驳回」下 | 名称对不上就挂空 |

没有 HTTP 的能力（MQ、定时任务、纯校验）可以不写接口，允许为空。

## 最小完整模板

把下面保存为 `知识.md` 上传即可。把名称和路径换成当前领域。

```markdown
# 模块业务知识

场景：示例场景

功能点：列表示例
接口：POST /demo/list

功能点：提交示例
接口：POST /demo/submit
规则：提交时状态必须为待提交
```
