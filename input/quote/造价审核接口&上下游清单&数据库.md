# 造价审核流程分析

基于对授权仓库 `jz_quotation`（家装报价/造价系统）的源码梳理，以下是造价审核流程、涉及接口及上下游系统的完整分析。

---

## 一、业务背景与定位

- 本项目为**家装报价系统**，核心数据包括**报价单**、**造价单**（`jz_design_cost`，MySQL）、**造价单明细**（`jz_design_cost_detail`）。
- **造价审核（CostAudit）** 是"增益模式"业务线下的审核环节：设计师/管家提交造价单后，由配置系统的**审核专员**在 PC 页面进行审核（通过/驳回），审核通过后造价单落地生效。
- 造价审核 PC 页面由 `CostAuditApi`（本仓库的 RPC Provider）承接，页面 UI 封装在 `hddp-admin`（配置系统）中——注意 API 注释明确说明"**该接口封装在 hddp-admin，增加出入参 admin 也要加**"。

---


## 四、核心状态机与规则

**审核状态 `checkStatus`（`DesignCheckStatusEnum`，落库 `jz_design_cost.check_status`）：**

| code | 枚举 | 含义 |
|---|---|---|
| 0 | INIT | 待提交 |
| 10 | SUBMITED | **待审核** |
| 20 | PASS | 审核通过 |
| 30 | REJECT | 审核拒绝 |
| 40 | CANCEL | 已取消 |
| 50 | INVALID | 已失效 |

**审核时效（`DesignCostAuditConstant`）：**
- 初审时效：**20 分钟**（`FIRST_AUDIT_TIME_LIMIT`）
- 复审时效：**15 分钟**（`AGAIN_AUDIT_TIME_LIMIT`）
- 即将超时判定：**10 分钟**（`ABOUT_TIME_OUT_MS`）
- 审核有效时间段：**9:00–22:00**（`AUDIT_VALID_START/END`）

> 审核通过/驳回的依据：`checkLog` 字段（JSON 数组）记录每次审核动作，`o`=状态码、`u`=审核人、`t`=时间。通过=20/驳回=30；`checkLog` 中只要有驳回记录即判定为"复审"（`againCheck`）。

## 五、关键业务逻辑分点解析

### 1. 列表查询 `findCostAuditList` / `costAuditSelectDb`
查询主表 `jz_design_cost`，按多条件组装：
- 待接单（`WAIT_ACCEPT`）：`check_status=10(SUBMITED)` 且 `audit_user_code IS NULL`
- 我的审核：按 `audit_user_code` 过滤，默认排除失效(50)
- 超时/即将超时：基于 `expected_audit_time`（预计审核时间）与当前时间比对
- 标签（首单/改价/复审）：按 `label` 模糊匹配
- 评价状态：`evaluate_state` + `evaluate_end_time` + `evaluate_score`
- 排序：待审核按 `urgent_review_time desc, field(check_status,10,30,20), expected_audit_time`；待接单按 `urgent_review_time desc, expected_audit_time`

列表同时**批量调用外部系统**填充：资产增益方案（ArchiveAdaptor）、AI 房源品质（HouseQualityAdaptor）、改前品质评级（QualityRatingAdaptor/LfOrderInfoAdaptor）、审核人姓名（PersonAdaptor）、评价单（`jz_design_cost_evaluate`）。

### 2. 接单 `accept`
将 `design_cost_code` 对应的造价单的审核人更新为当前用户：
```java
set(audit_user_code, req.userCode)
set(audit_user_name, req.userName)
```
（状态本身仍为 SUBMITED，仅绑定审核人）

### 3. 转派 `transform`
批量更新审核人为目标用户，并**异步发送企微消息**（`DesignCostAuditConstant.TRANSFORM_MSG`）通知新审核人。

### 4. 催审 `urgentReview`
将 `urgent_review_time` 置为当前时间（列表按此字段置顶），不影响状态机。

### 5. 审核通过/驳回（核心落地）
- **自动审核** `autoSubmitDesignCost`（约 L876）：`check_status→PASS(20)`，`approve_user_code→SYSTEM_USER`，打标签后调 `checkDesignCost`。
- 人工审核的通过/驳回由审核动作写入 `check_status` + `checkLog` + `approve_user_code` / `reject_reason`，驳回原因通过字典表 `quotationsDictionaryService.getRejectReasonInfo(REJECT_REASON, ...)` 翻译展示。

> ⚠️ 说明：本仓库（报价系统）主要承载**审核数据查询、列表、接单/转派/催审**；审核通过/驳回的**页面动作**大概率由 `hddp-admin`（配置系统）发起，再通过 RPC/事件反写回 `jz_design_cost`。仓库内未找到直接暴露给审核页面的"通过/驳回"HTTP 端点（只有查询类和自动审核），这属于**系统边界**，如需确认需结合 hddp-admin 侧代码。

# 方向1：`checkDesignCost` 审核落地方法深度追踪

这是造价审核**通过/驳回的核心落地点**（`DesignCostServiceImpl.java` L1894），所有审核动作最终都汇聚到这里。以下按执行顺序拆解完整逻辑链。

---

## 一、方法签名与前置约束

```java
public List<String> checkDesignCost(DesignCost designCost,
        List<DesignCostDetailCheck> designCostDetailChecks,
        Boolean autoCheck, Integer checkStatus)
```

- 返回 `errorMsg`（校验失败信息集合，为空才真正落库）
- 调用来源（已确认 3 处）：
  - `autoSubmitDesignCost`（L881）——自动审核，`autoCheck=true`
  - L685 / L1486 —— 其他提交/审核入口，`autoCheck=false`，携带明细审核记录与目标状态

---

## 二、步骤 1：审核前置强校验（整租 & 非心舍毛改）

通过 `quotationsManager` 查报价单 → 取产品版本，当 `type==2`（整租）且非"心舍&&毛改"时，强制校验：

| 校验 | 外部调用 | 拦截条件 |
|---|---|---|
| 定制设计模式判断 | `designCostManager.isCustomDesignMode` | — |
| 标准溢价场景判断 | `lfOrderInfoAdaptor.hasStandardPremiumScene`（立峰订单系统） | — |
| 改前评级单必须存在 | `qualityRatingAdaptor.getBeforeOrderBatch`（品质评级系统） | 列表为空 → 抛 `QUALITY_RATING_ORDER_INVALID` |
| 改前评级状态 | 同上 | `AUDITING` → "请先完成改前评级审核"；通过审核时状态非 `COMPLETED` → 禁止审核 |
| AI 房源品质评级 | `houseQualityAdaptor.batchGradeByOppIdsAndSource` | `isAuditing()` → 禁止；通过审核但非 `isAuditPass()` → 禁止 |

> 语义：**人工审核通过前**，相关前置评级单（改前评级、AI 房源品质）必须先审核通过，否则直接抛异常阻断。

---

## 三、步骤 2：SKU 明细审核处理（`autoCheck` 分支）

**自动审核（`autoCheck=true`）→ `saveDesignCostDetailCheck`（L2135）**：
1. 直接将该造价单全部明细 `jz_design_cost_detail.check_status` 置为 `PASS(20)`
2. 为每条明细生成 UUID 审核记录，批量插入 `design_cost_detail_check`（SKU 审核记录表）
3. 强制 `checkStatus = PASS`

**人工审核（`autoCheck=false`）：**
- 状态为 `PASS` → `designCostDetailManager.passDetail(...)` 置明细通过，并**异步**触发 `generateZDEvaluateCostApprove`（生成 ZD 评价造价审核员的评价单）
- 状态非 `PASS` 且传了 `designCostDetailChecks`（驳回场景）→ 为每条明细绑定 `design_code_detail_id`（通过 itemCode 关联明细 ID），在事务中**批量保存审核记录 + 更新 SKU 审核状态**

---

## 四、步骤 3：主表状态与时效/生效时间

```java
designCost.setCheckStatus(checkStatus);
if (PASS) { validTime = now; invalidTime = validTime + 15天; }
```

- **审核通过**：设置 `valid_time`（生效）与 `invalid_time`（15 天失效）
- **长租锁库存版本**（`QuotationUtil.judgeNeedLockStockAndExpire`）：失效期改为 **30 天**（L2028-2033）

---

## 五、步骤 4：写 `check_log` 审核日志（JSON 数组追加）

每次审核在 `jz_design_cost.check_log` 追加一条 JSON，记录：
- `u` = 审核人（姓名(工号) 或工号）
- `o` = 审核状态码（20/30）
- `t` = 审核时间
- `i` = 审核意见（`remark`）
- `p` = 本次总金额（`totalPrice`）
- `r` = 驳回原因（经 `quotationsDictionaryService` 字典翻译）

---

## 六、步骤 5：金额合规校验 `check`（L1831，仅通过时）

逐条明细校验：
1. 含税单价 = 不含税单价 × (1+税率)（允许 1 元误差，外采物品）
2. 金额小计 = 含税单价 × 数量（允许 1 元误差）
3. 全部明细金额之和 == 造价单总金额（±1 元）
- 买卖线产品版本（`RENTAL_GOODS_PRODUCTS`）：排除租赁物品后校验，`totalPrice = totalPrice - rentalTotalPrice`
- **校验失败 → 抛异常回滚 SKU 审核记录与状态**，不落库

---

## 七、步骤 6：落库与下游通知

**① 主表落库（`DesignCostMapper.xml` L139，已确认 SQL 列名）：**

```sql
update jz_design_cost
set APPROVE_USER_CODE = #{approveUserCode},
    CHECK_STATUS = #{checkStatus},
    CHECK_LOG = #{checkLog},
    reject_reason = #{rejectReason},
    design_cost_tag = #{designCostTag}
    [, INVALID_TIME = #{invalidTime}]
    [, VALID_TIME = #{validTime}]
where DESIGN_COST_CODE = #{designCostCode}
```

**② 发送造价单状态变更 MQ（`sendCheckResultOfDesignCost`，L295）**：
- 发送 `designCostCode / productId / checkStatus / remark / userCode` 到 `designCostExchange.exchange` + `designCostExchange.routingKey`（Apollo 配置），供下游消费（如订单/库存/其他系统联动）。

**③ 审核通过后处理（`handlePassDesignCost`，L2111）**：
- 长租锁库存版本：发送 **30 天延迟消息**（`foxyMessageManager`，`DESIGN_COST_EXPIRE_KEY`）用于到期作废
- 异步发送 `DesignLockStockEvent`（EventBus）**预占库存**

**④ 企微通知（`sendWecom`，L2100）**：
- 驳回（REJECT）且有 ZD 码 → 发企微消息通知 ZD（"造价审核单被驳回"）

## 十、关键实现备注（供研发参考）

1. **金额校验有 1 元容差**（`NumberUtil.isGreater(..., BigDecimal.ONE)`），且含税单价换算用 `(1+税率)` 而非 `/(1-税率)`，外采物品存在误差容忍的注释说明。
2. **自动审核**跳过前置评级校验、直接通过明细；**人工通过**才校验评级单与生成评价单。
3. **驳回场景**只有在传了 `designCostDetailChecks` 时才写 SKU 审核记录；若只改主表状态则明细不受影响。
4. `sendCheckResultOfDesignCost` 的 MQ 交换机/路由键为外部配置（Apollo），下游消费方需结合消息平台确认。
